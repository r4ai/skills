# 研究発表スライド

ゼミで論文や手法を紹介するスライドを作る。
聞き手は同じ分野の研究者で、発表者は話しながら一枚ずつ送る。
スライドは読ませる文書ではなく、話の要点と図を示す道具として作る。

## 見た目と文体

- 背景は白にする。文字は大きくし、細かい文字を出さない。本文は 44px 以上、図のラベルは 36px 以上、余白の ※ 注記でも 30px を下回らない（1920×1080 の画面での大きさ）。
- 「目的」「知りたいこと」の行や表、数式も本文と同じく大きくする。小さい文字で情報を詰めない。
- 「知りたいこと：」「目的：」のような導入の語の後で改行し、問いの本文を次の行に置く。
- タイトルは内容を表す名詞句にする。AI が作ったような飾りの見出し（「〜の真髄」「〜を解き明かす」など）や、無駄なサブタイトル、サブヘッダーを付けない。
- タイトルは簡潔にし、評価を含めずニュートラルにする。長くなるときは意味の切れ目で改行し、2 行までに収める（表紙も同じ）。図を置くスライドでは、タイトルが図に重ならないよう 1 行に収める。
- 箇条は短い体言止めにする。長くなるなら二つに分けるか、ネストする。箇条に文章を詰めない。
- 箇条は見出しと中身に分けて適切にネストし、構造が見えるようにする。同じ階層に性質の違う項目（結果と考察、条件と結論、前回と今回など）を並べない。
- 結果を大きな数字で強調しない。表現は学術発表の調子でニュートラルにする（「劇的に」「圧倒的」などを使わない）。
- 日本語の不自然な改行を出さない。文節で折り返す設定を入れ（references/html-deck.md）、2 文字だけ次の行に落ちる箇条は言い換えて 1 行に収める。

## 構成

- 用語は定義してから使う。定義より前のスライドでは、その語を避けるか「後で定義する」と添える。
- 説明と、それを示す例は隣に置く。たとえば手法 A と B の比較を述べた直後に、論文の例で A と B の違いを見せる。
- 一枚に詰め込みすぎない。責務の違う内容（考え方と場合分け、方法と結果、結果と解釈など）は別のスライドに分ける。
- 話の大きな区切りには「まとめ」を一枚置く。そこまでの要点を節ごとに短い箇条で並べる。
- 本筋から外れる応用（プロファイルによる選択、拡張の議論など）は、本筋を説明し終えてから置く。
- 発表時間に入りきらない補助の説明は、削らずに hidden（既定で非表示、ボタンで表示）にする。ページ番号は表示中のスライドだけで振り直す。
- 付録は「入力の形 → 問題になる箇所 → 変換と結果 → 実測」の型で例ごとにそろえ、タイトルも「〇〇の形」「〇〇の結果」のように同じ型にする。

## 具体例と図

具体例が発表の中心になる。読み手が式だけで理解することを期待しない。

- アルゴリズムや解析の過程は、図（フローチャート、グラフ、表）を見せながら一手ずつ進める。一枚で進めるのは一歩だけにする。
- 各ステップに「何のための計算か」を一行で置く（例：「知りたいこと：この時点で〇〇が成り立つか」）。
- 一つの概念は一枚に分ける。似た概念（取り得る値の種類、場合分けの各場合）を一枚に押し込まず、それぞれを例の図で示す。
- 同じ図で値だけが変わるコマは、図の要素の位置を完全に同じにする。ページ番号ではこれらを 1 ページの複数コマとして数える。
- 変換の例は before と after の両方を図で示し、after には疑似コードも添える。コードの書き方は図の形に合わせる（図とコードで制御構造の書き方を変えない）。
- 図にはコードの文をすべて入れる（カウンタの更新や入口の判定のような地味な文も省かない）。省くと図から導く結論が変わることがある。
- 新しい要素は、それが必要になるスライドで初めて図に出す（ある手順で作られる要素を、その手順のスライドより前に描かない）。
- 強調の帯や枠は、囲む要素に対して上下左右の余白をそろえる。片側だけ余白がないと、ずれて見える。
- 図で何かを省くときは、省いたことと理由をスライドかノートに書く。省略に気づいた聞き手は、図が誤っていると受け取る。
- 式や図の値が「どの対象についての値か」を添字で明示する（`f_{A}(n)`、`S_{A→B}` など）。添字がないと、別の対象や別の向きと取り違えられる。
- 論文の図を優先して使う。自分で描いた例、模式図、実際の出力と形が違う図は、スライドかノートにそう明記する。
- 例は最小にする。結論に関係しない要素を入れない。一方で、結論が変わる要素（繰り返し、分岐、副作用）は省かない。

## レイアウト

- 図は左、説明の列は右に置き、説明の列の位置と幅を全ページで固定する。ページを送っても文字の位置が動かないようにする。
- 図のラベル（分岐の真偽、辺の名前など）を線や箱に重ねない。値の注記を並べるときは、隣の注記と区別できる間隔を取る。
- 余白に足す注記は、本文のパネルや図に重ならない位置に置く。パネルの下の余白が足りなければ、ノートへ回す。
- 長い式は改行し、左揃えにする。右端で切れたまま公開しない。
- 新しく作ったスライドは、既存のスライドと箇条の位置、タイトルの型、ラベルの置き方をそろえ、読み手の負荷を下げる。

## 事実の確認

スライドの主張は、出典か実物で確かめてから載せる。
質問や指摘を受けたときも、鵜呑みにせずに確かめてから直す。

- 論文から引いた数値は、原文で分母と条件を確かめる（静的か動的か、どの集合の割合か、どの条件での比較か）。原文の直訳で意味が伝わりにくい用語は、スライドでは平易に言い換える。
- 論文の内容の要約は、原文と突き合わせる。可能なら別の担当（サブエージェント）に原文とスライドを渡して独立に照合させる。
- 「既存手法ではできない」「この変換で可能になる」という主張は、モデルや手計算だけで断定しない。実装のソースや実バイナリで確かめる。最適化レベルで結果が変わることがある。
- 手で解いた計算例（方程式の解、変換後の図、場合ごとの回数）は、小さなスクリプトで検算する。全ての場合を列挙できる大きさなら列挙する。
- 式と、実装や補足の文が食い違ったら、どちらが正しいかを実装で確かめてから直す。式が補足より広い（条件が足りない）こともある。
- 指摘が誤っていると分かったら、その根拠（試した入力と結果）を添えて、指摘とは違う直し方をする。

## 実装

HTML の発表資料として作る。
組み立ての手順、雛形、落とし穴は references/html-deck.md にある。

- `assets/template.html`：1920×1080 の舞台、ナビゲーション、ノート、hidden ボタン、日本語の改行の設定
- `scripts/deck.py`：スライドの組み立て。KaTeX のサーバー側描画、BudouX の文節、同じ図のコマ数え、hidden
- `scripts/check_deck.mjs`：headless Chromium で全コマを表示し、はみ出し、数式の切れ、短い最終行を報告して画像を保存する
- `scripts/example_build.py`：使い方の例

## 公開前の点検

1. 全コマで `check_deck.mjs` が overflow と clip を 0 件と報告する。
2. 変えたスライドの画像を目で見て、ラベルの重なり、矢印の欠け、不自然な改行がないことを確かめる。
3. 同じ図のコマが 1 ページにまとまり、hidden を切り替えるとページ番号が振り直されることを確かめる。
4. 数値と主張の出典（論文の箇所、実装のファイル、実測の条件）をノートに書いた。
5. 自作の例、模式図、未確認の点をスライドかノートに明記した。
