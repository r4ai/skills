# コードの複雑度を最小化する

外部契約を満たす最小のプログラムを作る。
実測された性能要件がない限り、実行速度や理論上の計算量より、理解と変更のしやすさを優先する。
複雑さを関数内の分岐数だけで判断せず、保持する状態、状態遷移、データ変換、責務の散在、構成要素をまたぐ内部知識まで数える。

## 判断の優先順位

次の順序で設計を評価する。

1. 正しさと外部契約
2. データ構造と状態遷移の単純さ
3. 責務の凝集度と依存関係の単純さ
4. 認知的複雑度
5. 循環的複雑度
6. コードサイズ
7. 実測で必要と判明した性能

認知的複雑度と循環的複雑度を、コードに対する最優先の数値指標として扱う。
ただし、指標を下げるために契約を破ったり、処理を意味のない小関数へ移したりしない。

性能を理由に複雑な表現を導入する場合は、入力規模、測定結果、必要な改善幅を示す。
根拠がなければ、少量データに対する線形探索や限定的な二重ループを許容する。

コードサイズの最小化は、同じ契約をより少ない概念、状態、分岐、変換で表すことを意味する。
コードゴルフ、名前の短縮、可読性の低下、必要なテストや契約文書の削除によって行数を減らさない。

## 契約違反を即座に失敗させる

契約による設計を使い、事前条件、事後条件、不変条件、失敗条件を変更前に定める。
不正な値を有効な値らしく変換する防御的プログラミングを行わない。

- 欠損値を空値、ゼロ、既定値へ黙って置換しない。
- 範囲外の値を切り詰めず、未知の列挙値を既知の値へ丸めない。
- 解析失敗を無視せず、推測した形式で再解釈しない。
- 例外を握り潰さず、成功に見える fallback を返さない。
- 起こらない状態に備えた null チェック、分岐、ログ、例外変換、再試行を追加しない。

信頼境界では、外部契約が要求する入力検証を一度だけ行う。
利用者が訂正できる入力エラーは、契約で定めた明確なエラーとして返す。
境界を通過した値は契約を満たすものとして扱い、後段で同じ検証を繰り返さない。

内部の事前条件と不変条件は、簡潔な `assert`、`panic`、`precondition`、`check` などで表し、違反時に即座に停止する。
本番ビルドで無効になる `assert` に正しさを依存させる必要がある場合は、常時有効な同等機構を使う。
契約違反から処理を続けるための補正や復旧を加えない。

障害回復、後方互換、可用性、セキュリティ上の拒否処理が外部契約に含まれる場合は、その契約を実装する。
この場合も、復旧を推測で広げず、必要な処理を境界へ隔離する。

## データから単純化する

制御フローを直す前に、分岐を生んでいるデータ表現を直す。

- 一つの概念を一つの値または構造にまとめ、同期が必要な並行配列や並行マップを避ける。
- 同じ事実を複数箇所に保存せず、導出できる値は必要な場所で導出する。
- 文字列、添字、ID、参照の相互変換を繰り返さず、処理中の正準な識別子を一つに決める。
- 順序が意味を持つなら、順序が表現に現れる単純な列を使う。
- 集合演算が本質でなければ、重複排除だけのために集合や索引を導入しない。
- 中間 DTO、キャッシュ、索引、対応表は、それが削除する複雑さより自身の維持コストが小さい場合だけ置く。
- 不正状態を表現できない型を選び、複数の真偽値の組合せで状態を表さない。
- 永続化形式、転送形式、ドメイン表現を機械的に分けず、意味または契約が変わる境界でだけ変換する。

パフォーマンスが要件を満たす限り、特殊化されたデータ構造より、標準的な列、レコード、直和型、マップを優先する。
各データ構造は、その意味と不変条件を一文で説明できる形にする。

## 責務と依存関係を単純化する

同じ不変条件を守り、同じ理由で変更される状態と操作を一つの構成要素にまとめる。
構成要素の外へ公開する知識を減らし、変更の影響範囲を狭める。

- データの所有者を一つに定め、その不変条件を守る操作を所有者の近くに置く。
- 呼び出し側には必要最小限の契約だけを公開し、内部表現や処理手順を知らせない。
- 依存の向きを入口から中核処理へそろえ、循環依存、共有可変状態、遠隔の状態変更を避ける。
- 工程ごとに機械的に層やクラスを分けない。
- 同じ内部表現を複数の層が知るだけの分割を行わない。
- 安定した契約の背後に実装を隠し、呼び出し側が知る事柄を減らせる場合だけ抽象化する。
- 実装が一つしかないインターフェース、委譲だけのラッパー、将来用の拡張点を作らない。
- ヘルパー関数は意味のある操作または契約を分離するときだけ作る。
- テストのためだけに内部表現を公開せず、公開契約または狭い構成要素を通して検証する。

## 制御フローと変数を単純化する

主処理をデータの選択、変換、集約として読める形にする。
命令的な処理が契約や状態遷移を明確にする場合は、宣言的な形へ無理に置き換えない。

- 入力の解析、検証、構築、実行を区別し、検証済みの不変条件を後段で再検証しない。
- 対象外の要素を入口で除き、主処理の分岐を減らす。
- 深いネストをガード節、フィルタ、変換、パターンマッチへ置き換える。
- 条件分岐がデータの対応関係を表すだけなら、表、マップ、列挙型の操作として表す。
- 宣言的な標準 API が意図を短く示す場合は、手書きのループより優先する。
- 可変変数を減らし、値のスコープを使用箇所の近くへ限定する。
- 長い処理の途中で意味が変わる変数を再利用しない。
- 暗黙の時系列に依存する更新を避け、各段階の出力を明示する。
- 例外的な一件のために全体へ状態や分岐を追加せず、境界で処理する。

短い関数自体を目標にしない。
関数を分けるたびに、読み手が追跡する名前、引数、戻り値、呼び出し先が増えることを考慮する。

## 複雑度を実質的に減らす

認知的複雑度を下げるため、ネスト、非局所的な状態変更、長寿命の変数、否定条件の連鎖、制御フローの飛躍を減らす。
循環的複雑度を下げるため、仕様差ではない分岐、重複した検証、フラグによるモード切替を削除する。

複雑度の指標を別の場所へ移動しただけの変更を改善と数えない。
次の変更は、状態または実行経路の総数が減った場合だけ採用する。

- 分岐を複数の小関数へ分散する。
- 条件式を名前だけのヘルパーへ隠す。
- 一つの処理をクラス、サービス、アダプターへ機械的に分割する。
- 明示的な分岐を設定、コールバック、継承、メタプログラミングへ移す。

## 実装手順

1. 変更対象の外部契約、失敗条件、既存テストを確認する。
2. プロジェクトで利用できる同じ測定方法を使い、変更前の行数、認知的複雑度、循環的複雑度を記録する。
3. 必要な状態、状態遷移、変換、責務、依存先を列挙する。
4. 削除できる状態、重複表現、中間層、漏れ出した内部知識を先に探す。
5. 期待する外部挙動をテストで固定する。
6. バグ修正では再現テストを先に作り、修正前に失敗することを確認する。
7. 状態遷移表から正常系、境界値、契約違反を抽出し、適切な粒度の単体、結合、E2E テストで覆う。
8. 最も単純なデータ表現から実装し、同じ理由で変わる状態と操作をまとめる。
9. テストを通した後、重複、分岐、変換、補助型、不要な依存をもう一度削る。
10. 変更後を同じ方法で測定し、認知的複雑度と循環的複雑度が悪化していないことを優先して確認する。
11. format、静的解析、関連テスト、カバレッジ測定を実行する。
12. 関連する契約、設計文書、利用方法が実装と一致していることを確認する。

測定ツールがない指標は推測しない。
導入コストが変更規模に見合わない測定基盤を、この指標のためだけに追加しない。

## レビュー基準

次の問いに答えられない実装は、さらに単純化する。

- 各データ構造の意味と不変条件を一文で説明できるか。
- 同じ事実の所有者が一箇所に定まっているか。
- 同じ理由で変わる状態と操作が一箇所にまとまっているか。
- 各構成要素は、契約に不要な他の構成要素の内部表現や処理手順を知らずに済むか。
- 各変換は外部境界または意味の変化に対応しているか。
- 分岐は実際の仕様差を表し、表現上の都合を補修していないか。
- 不正なデータを黙って補正、置換、無視していないか。
- 契約違反は発生箇所の近くで明確に失敗するか。
- 削除しても契約が変わらない層、型、キャッシュ、検証、fallback が残っていないか。
- 将来の要求を先回りした一般化、設定、拡張点が残っていないか。
- 変数のスコープと可変期間をさらに短くできないか。
- 性能上の複雑さには測定結果があるか。
- 指標の改善が関数分割による見かけ上の移動ではなく、状態と経路の削減になっているか。

## 完了報告

変更前後のコード量、認知的複雑度、循環的複雑度を、測定できた範囲で報告する。
測定できない指標は推測せず、未測定と書く。
削除した状態、分岐、変換、依存関係があれば併記する。
性能との交換条件を選んだ場合は、単純さを優先した箇所、測定結果、適用可能な入力規模を示す。
