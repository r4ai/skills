# コードの複雑度を最小化する

外部契約を満たす最小のプログラムを作る。
複雑さを分岐や行数だけで判断せず、保持する状態、状態遷移、データ変換、責務の散在、依存関係、読み手が追跡する場所の数まで評価する。
実測された性能要件がない限り、実行速度や理論上の計算量より、理解と変更のしやすさを優先する。

## 正しさを評価の前提にする

正しさと外部契約を、複雑度より先に満たすゲート条件とする。
許可なく契約を狭めたり、失敗条件を削ったり、テスト対象を除外したりして指標を改善しない。
既存テストを契約の全体と見なさず、テスト済みの入力だけをハードコードして正しさを装わない。

次の順序で設計を評価する。

1. 正しさと外部契約
2. データ構造と状態遷移の単純さ
3. 責務の凝集度と依存関係の単純さ
4. 認知的複雑度
5. 循環的複雑度
6. コードサイズ
7. 実測で必要と判明した性能

認知的複雑度と循環的複雑度を、コードに対する最優先の数値指標として扱う。
ただし、一つの指標へ集約した点数や加重平均を作らない。
複数の値を一つにまとめると、一項目の悪化を別の項目の改善で隠せるためである。

リファクタリングでは、少なくとも一項目を改善し、対になる指標を理由なく悪化させない変更を選ぶ。
機能追加とバグ修正では、必要な契約を満たす候補間で指標群を比較し、避けられない増加を最小にする。
指標間の交換条件が残る場合は、どの値をなぜ悪化させたかを報告する。

## 測定範囲を固定する

変更前に、測定対象、除外対象、ツール、バージョン、設定を固定する。
変更後も同じ条件で測り、都合のよいファイルや関数だけを抜き出さない。

測定対象には、変更したコードだけでなく、変更した動作を成立させる手書きの成果物を含める。
設定、SQL、テンプレート、スキーマ、マイグレーション、コード生成元へ判断を移した場合も測定対象に含める。
生成物と外部ライブラリのコードは除外し、生成元と新しく追加した直接依存を記録する。

テストとドキュメントはコードサイズ最小化の対象から除外する。
ただし、正しさのゲートと完了条件からは除外せず、削除による指標改善を認めない。

プロジェクトに測定ツールがない指標は推測しない。
導入コストが変更規模に見合わない測定基盤を、指標のためだけに追加しない。
測れない項目は、同じ意味を持つ構造上の個数を手作業で数えるか、未測定として理由を書く。
手作業で数える場合も、対象と数え方を変更前に決め、変更後に規則を変えない。

## 指標を組で評価する

各対象を、局所値、全体値、別表現への移動を検出する対抗指標で評価する。
利用可能な値だけを選ぶ場合も、局所値と全体値のどちらか一方だけにしない。

| 対象 | 局所値 | 全体値 | 対抗指標 |
| --- | --- | --- | --- |
| 制御フロー | 関数ごとの認知的複雑度と循環的複雑度の最大値 | 両複雑度の合計値と閾値超過関数数 | 関数総数、最大呼び出し深度、再帰的な呼び出し循環、処理を追う関数、構成要素、ファイルの数 |
| コードサイズ | 関数または構成要素ごとの整形後の行数 | 手書きの本体コードの総行数と、利用可能なら論理文数またはトークン数 | 関数、型、公開シンボル、重複ブロックの総数と、動作を決める設定、SQL、テンプレートの量 |
| 状態 | 構成要素ごとの意味上の状態数 | 到達可能な状態数と許可された状態遷移数 | 独立して変化する可変状態数、重複して保存する事実数、同期状態数、実行時に守る不変条件数 |
| データ表現 | 一つの概念に使う表現数 | 表現変換数と保存する事実数 | キャスト、動的キー参照、nullable、真偽値フラグ、型で表せない制約の数 |
| 依存関係 | 構成要素ごとの最大 fan-out（外向き依存数） | 依存辺総数、循環依存数、強連結成分数 | グローバル、サービスロケーター、イベント名、設定キー、外部サービスなどの暗黙または実行時依存数 |
| 責務 | 構成要素ごとの不変条件群または変更理由の数 | 構成要素の最大サイズと公開契約の総数 | 巨大な構成要素への統合、委譲だけの分割、内部表現を共有する構成要素数 |
| 公開 API | API ごとの引数と動作モードの数 | 公開シンボル、引数、契約上の動作ケースの総数 | 真偽値オプション、文字列モード、汎用マップ、動的ディスパッチの数 |
| テスト | 状態遷移表の各ケースに対応するテストの有無 | 行、分岐、状態遷移のカバレッジ | 測定除外、契約結果を確認しないテスト、利用可能ならミューテーションスコア |

意味上の状態とは、外部挙動または許可される操作が異なる状態を指す。
連続値や大きな入力集合の各値を、別々の状態として数えない。
処理を追う箇所数は、代表的な外部操作を入口から結果まで追うときに通過する関数、構成要素、ファイルを同じ基準で数える。

認知的複雑度と循環的複雑度では、最大値と合計値を必ず併記する。
関数分割で最大値だけを下げる変更は、関数総数、合計値、呼び出し深度で検出する。
巨大な関数へ統合して総数を減らす変更は、最大値と構成要素の最大サイズで検出する。
閾値超過関数数を使う場合は、プロジェクトで定めた閾値を固定し、変更の途中で変えない。

意味上の状態数と選択肢数を、フィールド数や構文上の分岐数で代用しない。
状態を整数、文字列、ビット列へ符号化しても、到達可能な状態と遷移が同じなら削減と数えない。
分岐をテーブル、ハンドラー、ポリモーフィズム、例外、設定、DSL へ移しても、動作を選ぶ規則が残るなら削減と数えない。

コードサイズは、プロジェクトの formatter を適用した状態で測る。
複数の文を一行へ詰めること、名前を短くすること、巨大な式や正規表現へ圧縮することを削減と数えない。

依存辺を減らすために巨大な構成要素へ統合しない。
構成要素を細分化して各要素の責務数だけを下げない。
依存関係と責務は、辺の総数、最大 fan-out、構成要素の最大サイズ、公開契約の総数を組にして判断する。

公開シンボルを一つの汎用 API へ統合しても、文字列モード、真偽値オプション、引数の組合せ、失敗条件が増えるなら単純化と数えない。
外部ライブラリへ処理を委譲する場合は、削除した内部知識と、新しい依存の契約、設定、変換、失敗条件を比較する。

カバレッジの測定対象と除外規則を変更前後で固定する。
行カバレッジだけを改善せず、分岐と状態遷移のケースを契約に対応づける。

## 契約違反を即座に失敗させる

事前条件、事後条件、不変条件、失敗条件を実装前に定める。
不正な値を有効な値らしく変換する防御的プログラミングを行わない。

- 欠損値を空値、ゼロ、既定値へ黙って置換しない。
- 範囲外の値を切り詰めず、未知の列挙値を既知の値へ丸めない。
- 解析失敗を無視せず、推測した形式で再解釈しない。
- 例外を握り潰さず、成功に見える fallback を返さない。
- 起こらない状態に備えた null チェック、分岐、ログ、例外変換、再試行を追加しない。

信頼境界では、外部契約が要求する入力検証を一度だけ行う。
利用者が訂正できる入力エラーは、契約で定めた明確なエラーとして返す。
境界を通過した値は契約を満たすものとして扱い、後段で同じ検証を繰り返さない。

内部の事前条件と不変条件は、簡潔な `assert`、`panic`、`precondition`、`check` などで表し、違反時に即座に停止する。
本番ビルドで無効になる `assert` に正しさを依存させる必要がある場合は、常時有効な同等機構を使う。
契約違反から処理を続けるための補正や復旧を加えない。

障害回復、後方互換、可用性、セキュリティ上の拒否処理が外部契約に含まれる場合は、その契約を実装する。
この場合も、復旧を推測で広げず、必要な処理を信頼境界へ隔離する。

## データと責務から単純化する

制御フローを直す前に、分岐を生んでいるデータ表現と責務の配置を直す。

- 一つの概念を一つの値または構造にまとめ、同期が必要な並行配列や並行マップを避ける。
- 同じ事実を複数箇所に保存せず、導出できる値は必要な場所で導出する。
- 処理中の正準な識別子を一つに決め、文字列、添字、ID、参照の相互変換を繰り返さない。
- 不正状態を表現できない型を選び、複数の真偽値や nullable な値の組合せで状態を表さない。
- 中間 DTO、キャッシュ、索引、対応表は、それが削除する複雑さより自身の維持コストが小さい場合だけ置く。
- 永続化形式、転送形式、ドメイン表現を機械的に分けず、意味または契約が変わる境界でだけ変換する。

パフォーマンスが要件を満たす限り、特殊化された構造より、標準的な列、レコード、直和型、マップを優先する。
各データ構造は、その意味と不変条件を一文で説明できる形にする。
型や構造体の数だけを減らすために、汎用マップ、文字列キー、動的型へ情報を押し込まない。

同じ不変条件を守り、同じ理由で変更される状態と操作を一つの構成要素にまとめる。
データの所有者を一つに定め、その不変条件を守る操作を所有者の近くに置く。
呼び出し側には必要最小限の契約だけを公開し、内部表現や処理手順を知らせない。

依存の向きを入口から中核処理へそろえ、循環依存、共有可変状態、遠隔の状態変更を避ける。
工程ごとに機械的に層やクラスを分けない。
実装が一つしかないインターフェース、委譲だけのラッパー、将来用の拡張点を作らない。
抽象化は、呼び出し側が知る事柄と変更の影響範囲を実際に減らす場合だけ導入する。

## 制御フローと変数を単純化する

主処理をデータの選択、変換、集約として読める形にする。
命令的な処理が契約や状態遷移を明確にする場合は、宣言的な形へ無理に置き換えない。

- 入力の解析、検証、構築、実行を区別し、検証済みの不変条件を後段で再検証しない。
- 対象外の要素を入口で除き、主処理の分岐を減らす。
- 深いネストをガード節、フィルタ、変換、パターンマッチへ置き換える。
- 条件分岐がデータの対応関係を表すだけなら、表、マップ、列挙型の操作として表す。
- 宣言的な標準 API が意図を短く示す場合は、手書きのループより優先する。
- 可変変数を減らし、値のスコープと可変期間を使用箇所の近くへ限定する。
- 長い処理の途中で意味が変わる変数を再利用しない。
- 暗黙の時系列に依存する更新を避け、各段階の出力を明示する。
- 例外的な一件のために全体へ状態や分岐を追加せず、境界で処理する。

関数の短さ自体を目標にしない。
ヘルパー関数は、意味のある操作または契約を分離するときだけ作る。
関数を分けるたびに、読み手が追跡する名前、引数、戻り値、呼び出し先が増えることを考慮する。

## 性能上の複雑さを制限する

性能を理由に複雑な表現を導入する場合は、代表的な入力規模、測定条件、現在値、要求値、必要な改善幅を示す。
平均値だけで判断せず、要件に関係する遅延分布、スループット、メモリ量の値を選ぶ。
根拠がなければ、少量データに対する線形探索や限定的な二重ループを許容する。

キャッシュ、索引、並列化、特殊化されたデータ構造は、測定で必要と判明した範囲だけに置く。
性能改善後も、追加した状態、同期、無効化条件、失敗経路を複雑度の指標群へ含める。

## 実装と改善のループ

1. 外部契約、許可された契約変更、失敗条件、既存テストを確認する。
2. 測定範囲と測定条件を固定し、変更前の指標群を記録する。
3. 必要な状態、状態遷移、変換、責務、明示的な依存、暗黙の依存を列挙する。
4. 状態遷移表から正常系、境界値、契約違反を抽出し、期待する外部挙動をテストで固定する。
5. バグ修正では再現テストを先に作り、修正前に失敗することを確認する。
6. 最も単純なデータ表現から実装し、テストを通す。
7. 重複した事実、状態、分岐、変換、補助型、依存を削除する。
8. 変更後を同じ条件で測定し、局所値、全体値、対抗指標を比較する。
9. 複雑さが関数、構成要素、設定、動的ディスパッチ、生成元、依存先へ移っただけでないか確認する。
10. 正しさを保ったまま削除できる概念または経路がなくなるまで、手順7から9を繰り返す。
11. format、静的解析、単体テスト、結合テスト、必要な E2E テスト、カバレッジ測定を実行する。
12. 関連する契約、設計文書、利用方法が実装と一致していることを確認する。

テストは状態遷移表から抜けなく作り、テスティングピラミッドに従って最も狭い層で多く検証する。
利用可能ならミューテーションテストを使い、到達しただけで契約を検証しないテストを見つける。

## 改善を止める条件

次の問いを順に確認し、改善点が残る間は実装と改善のループへ戻る。

- 外部契約を狭めたり、失敗条件を削ったりして数値を下げていないか。
- 局所値の改善と引き換えに、全体値、要素数、追跡箇所を増やしていないか。
- 明示的な分岐を設定、ルール、コールバック、継承、例外、再帰、非同期処理、メタプログラミングへ移していないか。
- 状態や制約を整数、文字列、真偽値、nullable、汎用マップへ隠していないか。
- 同じ事実と不変条件の所有者が一箇所に定まり、重複して保存されていないか。
- 各変換と分岐は、外部境界、意味の変化、実際の仕様差のいずれかに対応しているか。
- 各構成要素は、契約に不要な他の構成要素の内部表現や処理手順を知らずに済むか。
- 依存辺を減らすために責務を巨大な構成要素へ集めていないか。
- 責務を細かく見せるために構成要素、公開契約、依存辺を増やしていないか。
- コードを減らすためにテスト、ドキュメント、型、名前、可読性を犠牲にしていないか。
- 内部コードを減らすために、同等以上の契約、設定、変換、通信、失敗条件を持つライブラリまたは外部サービスを追加していないか。
- 削除しても契約が変わらない状態、経路、変換、層、型、キャッシュ、検証、fallback が残っていないか。
- 性能上の複雑さには、代表的な入力と要求値に基づく測定結果があるか。

すべてに問題なしと答え、関連する検証が通った時点で完了する。

## 完了報告

変更前後の値を、同じ測定範囲と条件で表にして報告する。
測定対象、除外対象、ツール、バージョン、設定、閾値も併記する。
少なくとも、認知的複雑度と循環的複雑度の最大値と合計値、コード量、関数総数の各項目を表に含める。
変更に関係する状態、状態遷移、変換、依存辺、公開契約を数えられる場合は併記する。
測定できない指標は、推測値の代わりに未測定の理由を表へ記載する。

指標が悪化した場合は、必要になった契約と、採用しなかった単純な代替案を示す。
性能との交換条件を選んだ場合は、単純さを優先した箇所、測定条件、入力規模、適用限界を示す。
